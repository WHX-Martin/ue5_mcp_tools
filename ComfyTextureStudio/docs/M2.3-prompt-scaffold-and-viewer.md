# M2.3 · 提示词骨架丢失 & 预览窗口打不开

| 项 | 值 |
|---|---|
| 日期 | 2026-10-13 |
| 触发 | 用户报两件事：①「这次生成 PBR 贴图和基础色对不上」②「打开的预览窗口在我关闭后打不开了」 |
| 结论 | 两个真 bug，都已修复并验证。①的根因在**面板的提示词编辑逻辑**，不在 ComfyUI 也不在阶段B 工作流 |
| 影响面 | ①会让出图质量劣化且**完全静默**；②只影响预览体验 |

## 一、PBR 与基础色对不上

### 1.1 现象与第一手证据

用户那次运行（job `20261013-182742_9D0E1F`）：

| 产物 | 本次 | 之前的正常值（`20261013-110104_676802`） |
|---|---|---|
| 基础色 灰度 Laplacian 方差 | 618.8 | 735.8 |
| **normal 平均偏离平面** | **0.0191** | **0.1803** |
| **height 灰度 std** | **15.04** | **30.93** |

基础色本身只是略软（-16%），但 normal 几乎**全平**——大片纯紫、只剩几个孤立的星点。
这就是「对不上」的直接观感：贴图是密集石子，法线却告诉引擎这是一块平地。

### 1.2 排查路径（三步，每步都在排除一个假说）

**第一步：diff API 快照。** 阶段B 的参数逐节点对比，除了 jobId 前缀**完全一致**
（`fov=3 / pad=256 / iterations=5`，`low_freq_radius=96`，`bump_strength=31.4` …）。
阶段A 的差别却很大：

| 节点 | `110104`（正常） | `182742`（本次） |
|---|---|---|
| `3 CLIPTextEncode` | `mtrlx, seamless tileable PBR material, coarse pebbly sand, …, directional sunlight from upper left, visible bump relief with soft cast shadows, raking light, crisp fine detail, …` | **`coarse pebbly sand`** |
| `7 KSampler` | `dpmpp_2m` / `karras` | **`euler` / `simple`** |

**第二步：DSINE 是好的。** 单独提交「LoadImage → SeamlessDSINENormal → SaveImage」，
两张输入图各跑一遍（顺带保存 LoadImage 的输出，逐像素确认读到的就是原图）：

| 输入 | DSINE 输出的法线强度 |
|---|---|
| `182742` 那张基础色 | **0.2740** |
| `110104` 那张基础色 | 0.1409 |

DSINE 对本次那张图反而给出**更强**的法线 ⇒ 节点没问题、输入图也没问题。
衰减发生在它后面。

**第三步：完整复现阶段B，逐级存中间结果。** 用 `182742` 的工作流（换输入文件名避开节点缓存）
并把 `35 DSINE`、`36 FlattenNormal` 的输出也存下来：

| 级 | 指标 |
|---|---|
| ① DSINE 原始输出 | 平均偏离 0.2740 ✅ |
| ② FlattenNormal 之后 | 0.1650 ✅ |
| ③ HeightFromNormal → height | **std 15.04** ❌（正常 30.93） |
| ④ NormalFromHeight → normal | **0.0191** ❌ |

复现值与用户那次**逐位一致**（15.04 / 0.0191）⇒ 确定性问题，不是偶发。

### 1.3 根因：提示词骨架被静默丢弃，而采样器被探测悄悄改掉

**① 提示词只剩一条裸描述。**

`mtrlx`（LoRA 触发词）和 `directional sunlight / raking light / crisp fine detail`
这些 tag 全没了。它们不是装饰：**阶段B 的 DSINE 靠明暗反推几何**，
丢了方向光与高频细节，基础色就没有可供反演的几何线索，
`HeightFromNormal` 积出来的高度图对比度只有一半，`NormalFromHeight` 再放大就成了平地。

面板原本的设计是把提示词拆成「前缀（LoRA 触发词）/ 描述（用户编辑）/ 后缀（光照细节）」，
问题出在**每次编辑都重新推导骨架**：

```cpp
// 旧实现（已删）—— SComfyTextureStudioPanel.cpp 的 OnTextChanged
MaterialDescription = NewText.ToString();
const FPromptScaffold Scaffold = SplitPrompt(PositivePrompt);   // ← 从"已被重写过的"文本反推
if (!Scaffold.Prefix.IsEmpty() || !Scaffold.Suffix.IsEmpty())
{
    PositivePrompt = JoinPromptParts(Scaffold.Prefix, MaterialDescription, Scaffold.Suffix);
}
else
{
    PositivePrompt = MaterialDescription;                        // ← 骨架就此永久消失
}
```

`SplitPrompt` 是**启发式**（按关键词表识别前缀/后缀）。当描述被清空时，
整条文本都像"前后缀"，于是走到退化分支 `Last < First` → 返回空骨架。
而"全选 → 重新输入"必然经过空串这个中间态：

1. 用户全选删除 → `MaterialDescription = ""` → 重拼成 `前缀 + 后缀`（描述没了）
2. 用户输入第一个字符 `c` → 拿第 1 步的结果去 Split → 现在**整条都是** style/render token
   → `Last < First` → **退化 → `PositivePrompt = "c"`**
3. 骨架永久丢失。之后无论再打什么字，都只是纯粹的描述文本。

**② 采样器也从 `dpmpp_2m/karras` 变成了 `euler/simple`。**

`ProbeServer()` 拿到 `/object_info` 的真实枚举后无条件重置：

```cpp
if (SamplerOptions.Num() > 0) { SelectedSampler = SamplerOptions[0]; }     // ← ComfyUI 第一项就是 euler
if (SchedulerOptions.Num() > 0) { SelectedScheduler = SchedulerOptions[0]; }
```

同一段代码对 `LoraName` 是有 `ContainsByPredicate` 保护的，采样器这两行漏了。
于是「打开面板 / 点重新探测」这个动作本身就会把 manifest 的默认值换掉。
另外这两项的初值当时还是硬编码的字面量，没从 manifest 读。

### 1.4 修复

**提示词逻辑整体搬到 Runtime 模块新文件 `ComfyPromptScaffold.h/.cpp`**，不再放在面板的
匿名命名空间里 —— 那段逻辑正是因为不可测，缺陷才存在了那么久。

核心是 `FComfyPromptEditor`：**骨架只在两个时刻更新**（从 manifest 初始化、
用户在折叠区显式编辑完整文本），描述框怎么改都不会动它。

```cpp
void FComfyPromptEditor::SetDescription(const FString& InDescription)
{
    Description = InDescription;
    RebuildFromScaffold();          // 只换描述，骨架原样保留
}

bool FComfyPromptEditor::SetFullPrompt(const FString& InFullPrompt)
{
    const FComfyPromptScaffold Scaffold = Split(InFullPrompt);
    if (!Scaffold.HasScaffold())
    {
        Description = InFullPrompt; // 拆不出骨架 ⇒ 当它是新描述，**不覆盖骨架**
        RebuildFromScaffold();
        return false;
    }
    /* 拆得出 ⇒ 用户确实在改骨架，接受 */
}
```

配套：
- 面板在描述框下方显式显示骨架异常（有异常才显示），不再静默
- 提交阶段A 时把完整提示词与采样参数打进日志 —— 这次事故事后只能翻
  `stage_a_api.json` 才看出来，以后当场可查
- `PickValidOption()` 取代 `Options[0]`：优先保留当前值，其次回退 manifest 默认值
- 采样器/调度的初值改为从 manifest 的槽位默认值读

### 1.5 验证

新增 `-TestPromptScaffold`（**不需要 ComfyUI**），13 条断言全绿：

```
✓ ① 完整模板拆出骨架            前缀[mtrlx, seamless tileable PBR material] 后缀[square top-down surface, …]
✓ ① 拆分可逆（Join 回原串）
✓ ② 清空再重打后骨架仍在（★原 bug）        242 字
✓ ② 描述已换成新内容                      coarse pebbly sand
✓ ③ 裸描述拆不出骨架（启发式的固有行为）    前缀空=1 后缀空=1
✓ ④ 折叠区改成裸描述：不更新骨架
✓ ④ 折叠区改成裸描述：原骨架保留
✓ ⑤ 折叠区改骨架：更新成功且可逆
✓ ⑥ 提交文本含 LoRA 触发词
✓ ⑥ 提交文本含光照/细节 tag（阶段B 反演法线靠它）
✓ ⑥ 骨架状态报告为正常
```

用例 ② 直接复现原 bug 的时序；用例 ③ 是**反面对照** —— 它把"为什么必须缓存骨架"
钉在测试里（裸描述拆不出骨架是启发式的固有行为，任何"每次重新推导"的写法都必然出事）。

端到端复跑（`-Import -Seed=random`）：

| 指标 | 修复后 | 用户那次 | 正常参照 |
|---|---|---|---|
| 阶段A prompt 长度 / 含 `mtrlx` | 295 / ✓ | 只有 `coarse pebbly sand` | 295 / ✓ |
| 采样器 | `dpmpp_2m` / `karras` | `euler` / `simple` | `dpmpp_2m` / `karras` |
| **normal 平均偏离** | **0.1620** | 0.0191 | 0.1803 |
| **height 灰度 std** | **30.84** | 15.04 | 30.93 |

同样的阶段B 参数、同样的代码，只差 prompt 是否带骨架，法线强度差了 **8.5 倍**。

冷加载核对 `-VerifyOnly`：**41 项核对 0 项不符**（无回归）。

## 二、预览窗口关掉后打不开

### 2.1 现象与日志

```
18:29:20  Window '高度 · height_00001_.png' being destroyed      ← 用户关掉窗口
18:29:29  Window '法线 · normal_00001_.png' being destroyed
18:30:10  Interchange start importing source [.../stage_b/albedo_00001_.png]   ← 开始导入
18:30:14  导入完成，写 report_import.json
18:32:07  LogStreaming: Warning: Failed to read file '.../stage_b/normal_00001_.png' error.
18:32:07  LogComfyTextureStudioEditor: Warning: 查看器加载 PNG 失败：.../stage_b/normal_00001_.png
```

`stage_b/` 目录下的 6 个 PNG **全没了**，只剩 `stage_a/` 那张和 `report_import.json`。

### 2.2 根因

导入结束时会清理中转 PNG（`Settings::PreserveDownloadedPng` 默认 `false`
→ `Request.bDeleteSourcePng = true` → 删掉 `ChannelPngPaths` 里的每一个）。

而查看器**每次都重新读盘**：

```cpp
const TSharedPtr<FComfyPreviewTexture> Preview = FComfyPreviewTexture::LoadFromPng(PngPath);
```

于是造成一个很别扭的现象：**面板上的缩略图分明还在**（早在图还在的时候就加载进内存了），
**点开却没反应**。用户感受到的就是"我刚关掉它，就打不开了"——其实是导入把它删了。

### 2.3 修复

面板的两份缓存（`TMap<FString, TObjectPtr<UTexture2D>>` + `TMap<FString, TSharedPtr<FSlateDynamicImageBrush>>`）
合并成一份 `TMap<FString, TSharedPtr<FComfyPreviewTexture>> PreviewCache`，查看器**共享**同一份资源：

```cpp
// 走面板的缓存，不重新读盘
const TSharedPtr<FComfyPreviewTexture> Preview = GetPreviewTexture(PngPath);
```

用 `TSharedPtr` 共享之所以安全：引用计数保证「窗口活着 ⇒ 贴图活着」，
面板析构时它的引用减一而已，不会再出现「面板 `RemoveFromRoot` 了、窗口还在画」的悬空风险
（这与 M1 那个 HTTP 野指针是同一类生命周期问题，只是方向相反）。

顺带两处：
- 真正取不到时（文件没了 + 内存没副本）**弹通知说明原因**，而不是静默失败
- 「用系统看图器打开」按钮在文件已不存在时**禁用**（它依赖磁盘上的原文件）

### 2.4 未验证项

⚠ 这一步的**实际点击行为**只能在有 GUI 的编辑器里确认——沙箱起不了 Slate
（`FSlateApplication::IsInitialized()` 为 false，`-CtsTestPanel` 会优雅跳过）。
能自动验证的部分（编译、资源获取路径、缓存生命周期）已通过。

## 三、教训

1. **"启发式的输出"不能当作下一次推导的输入。** 每次从已被重写过的文本反推骨架，
   等于让误差自我累积；而退化分支恰好把"空描述"映射成"没有骨架"，
   两者叠加就成了静默的数据丢失。**要缓存的是意图（骨架），不是它的推导结果。**
2. **不可测的代码等于没写测试的代码。** 这段逻辑原来在 Slate widget 的匿名命名空间里，
   既不能单测也不能在 commandlet 里跑 —— 这才是缺陷能存活这么久的真正原因。
   搬出来之后，负向用例 ② 是**照着事故时序**写的，几分钟就能写完。
3. **负向用例要有个"反面对照"。** 用例 ③ 断言"裸描述拆不出骨架"，
   它不测我们的实现，而是把**为什么必须这么实现**钉住 ——
   否则后来者看到"缓存骨架"只会觉得是多余的状态。
4. **默认值不能写成列表第 0 项。** 第三方返回的枚举顺序与"我们希望默认哪个"无关。
   `LoraName` 那里本来就有正确写法，采样器两行漏了 —— 同一个函数里的一致性缺失最容易被忽略。
5. **文件被删不该让内存里的东西也失效。** 缩略图能显示、点开却打不开，这种
   "同一份数据的两个入口行为不一致"本身就是设计缺陷的信号。
